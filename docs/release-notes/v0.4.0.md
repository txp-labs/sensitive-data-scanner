## What 0.4.0 is

The first release since 0.2.0. **It includes 0.3.0**, which was prepared on
29 Sep 2026 and never published: there is no 0.3.0 tag, image or wheel, and
its changes are listed under 0.4.0 in the changelog.

The scanner now finds **card numbers, US Social Security numbers, ITINs and
dates of birth** across a whole AWS estate, in Azure and Google Cloud, in
databases hosted anywhere, and in Microsoft 365, Google Workspace, Slack,
Jira and Confluence. It runs inside your environment with read-only access,
and only findings leave it, never a value.

**Be clear about how much of this has run for real.** Whole-account scans
have run in two real AWS development accounts, and one SharePoint site has
been scanned in a test Microsoft 365 tenant. Azure, Google Cloud, every SaaS
source but SharePoint, most database engines, and the AWS stores listed under
"Not yet proven" are tested against simulated services only.
"Proven in a real account" below lists exactly what has run.

### What you get

- **A whole AWS estate, discovered.** Each run lists the data stores in its
  account and region and reads them, with no list for you to write: S3 and S3
  directory buckets, CloudWatch Logs, DynamoDB, Glue tables, OpenSearch,
  Kinesis and Firehose, Parameter Store, Timestream, Keyspaces, Step
  Functions history, Lambda environment variables, X-Ray traces, CodeCommit,
  and cache snapshots exported to S3. RDS and Aurora (by snapshot export),
  Redshift, EBS snapshots, SQS dead-letter queues, Secrets Manager (counts
  only), MSK, Amazon MQ, ECR images, SageMaker, Neptune Analytics and
  EventBridge archives are opt-in. One StackSet rolls it out across an
  organization.
- **Azure and Google Cloud.** Their own runners and images: Blob Storage,
  ADLS Gen2, Cosmos DB, Table and Queue Storage and Azure Monitor logs; Cloud
  Storage, BigQuery, Firestore, Spanner, Bigtable and Cloud Logging. Their SQL
  databases are opt-in. Deployed with Bicep or Terraform.
- **Databases hosted anywhere.** PostgreSQL, MySQL and MariaDB, SQL Server,
  Oracle, MongoDB, Snowflake and Databricks SQL, each with a user the runner
  first checks can only read. A user that can write is refused.
- **SaaS.** Microsoft 365 (mail, OneDrive, SharePoint; Teams opt-in), Google
  Workspace (Gmail, Drive), Slack, Jira and Confluence, from a container you
  run in your own environment.
- **Your vendor's findings, ours, or both.** Import Amazon Macie, Google
  Cloud Sensitive Data Protection, Microsoft Purview DLP, Google Workspace
  DLP or Slack DLP findings instead of scanning, or alongside it, with
  matching findings linked.
- **More of what's inside a file is read.** A file's content, not its name,
  decides how it's read. Zip, tar, gzip, bzip2 and xz archives, PDF text,
  and Word, Excel and PowerPoint files are read, and so are Parquet, ORC and
  Avro by column.
- **Smart rescans.** Each run reads what changed since the last one. An
  unchanged object is read again only when a part of the scanner that could
  change its result has changed. Unchanged database tables are skipped,
  large DynamoDB tables are read by export and then incrementally, big
  buckets are listed from their S3 Inventory, and duplicate copies are read
  once.
- **At-rest encryption on every finding**, and a PCI DSS note for your
  assessor on card findings.
- **A coverage report.** Every run lists every store it found, read or not,
  and why. Anything it can't read is a named gap, never a silent pass.
- **Detection, sharpened.** Spec 0.2 to 0.7: ITINs, answers keyed into a
  phone menu, an SSN's last four after "my", and fewer
  false alarms. A full timestamp is never taken for a date of birth.

### Proven in a real account

- **Whole-account AWS runs in two real development accounts.**
  - **mermera-dev, 30 Sep 2026:** 776 stores discovered in one account and
    region, 753 read over three runs, and the rest reported with a reason.
    Findings and logs held no values, and searching every output for the two
    detected values found none. CloudTrail shows no write by the scanner's
    role but to its own log stream (its three RDS export attempts were
    denied). The one finding was a false positive (two document dates in
    a code bundle).
  - **stugum-dev, 1 Oct 2026:** a whole-account run over 147 sources, with
    no values in its output and no leaks.
  - Together these have proven, by real reads, **S3, CloudWatch Logs,
    Lambda configuration, SSM Parameter Store, X-Ray, Step Functions and
    DynamoDB**.
- **DynamoDB, a named table.** The v0.2.0 run on 29 Sep 2026 read one table
  from an explicit configuration: 37 findings on the positive control, 0 on
  the negative.
- **Microsoft 365, one SharePoint site**, in a test tenant on 30 Sep 2026:
  72 files read, both planted findings found (a card in a Word file renamed
  as an image, and an SSN inside a zip), and no values in the output.
- **PostgreSQL 16 and MySQL 8.4** run against real engines in containers in
  CI. Read-only users are read, users that can write are refused, and the
  data is unchanged.

These runs found real problems, and **every one is fixed in this release**:
RDS export always being denied, decrypting log groups under a customer's
key, large stores starved of time when many share a run, a cold start past
Lambda's limit, extra runs from invoking by hand, a missing encryption
field, timestamps taken for dates of birth, and SharePoint site naming.
**The fixes are tested in CI and have not yet been re-run in a real
account.**

### Proven by tests (CI on every pull request)

- Every store on every platform, against simulated services or drivers:
  discovery, sampling, paging, budgets and resume, and each reason a store
  is reported rather than read.
- **No value leaves.** The no-leak suite plants made-up values in cells,
  documents, messages, parameters and in store, table and column names, and
  checks findings, events, logs, errors and object reprs for them.
- **Read-only.** The AWS IAM is checked against every call the code makes,
  and the Azure roles, Google Cloud roles and SaaS scopes are held by strict
  tests.
- **Accuracy.** A benchmark of precision and recall per class, with a
  regression gate. The readers are fuzzed against damaged and hostile files.
- Detection agrees across the Python engine, Presidio, and the TypeScript
  package.

### Not yet proven

- **Azure, Google Cloud and their deployments**: never run in a real tenant
  or organization.
- **SaaS other than one SharePoint site**: Microsoft 365 mail, OneDrive and
  Teams, Google Workspace, Slack, Jira and Confluence have never run against
  a real tenant.
- **SQL Server, Oracle, MongoDB, Snowflake and Databricks**: simulated
  drivers only.
- **AWS stores other than the seven above**, the opt-in reads (RDS and
  Aurora by export included), and the StackSet rollout across an
  organization: tested against simulated services only.
- **The vendor importers** (Macie, Sensitive Data Protection, Purview,
  Workspace DLP, Slack DLP): tested against simulated APIs only.
- **A complete first pass of a large account.** Neither whole-account run
  finished one: large log groups and busy buckets carry over to later runs.
- **The event-driven mode** is design only, and EFS and FSx need a
  file-system task that is designed and not built.
- **Releases are not signed yet** (docs/RELEASING.md). Verify downloads with
  `SHA256SUMS` and the SBOMs.

### Upgrading from 0.2.0

- The findings schema goes from 1.1 to **1.11**. Every step is additive: a
  consumer of 1.1 keeps working and can ignore the new fields.
- Detection code moved to its own package, `sensitive-data-scanner-core`: a
  Python import of `sensitive_data_scanner.detect` (or `.engine`, `.scan`,
  `.safety`, `.findings`) becomes `sensitive_data_core.detect`, and so on.
- The spec is now at 0.7. If you mirror it, follow `spec/README.md`'s
  "Changes from" sections from 0.1 on.
