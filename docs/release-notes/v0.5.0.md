## What 0.5.0 is

The first **signed** release, and the first you can deploy on AWS without
building anything: the Lambda code is published, signed, in seven AWS
regions. It also makes every deliberate limit of the scanner visible and
switchable, and it stops reading storage that costs money to read unless you
ask it to.

**Before 1.0 a change of default bumps the minor version, and this release
changes defaults** - read "Changed defaults" before you upgrade.

### What you get

- **Signed code in your region.** The Lambda zip is signed with AWS Signer by
  a `TxpLabsSensitiveDataScanner` profile in each of us-east-1, us-east-2,
  us-west-2, ca-central-1, eu-west-1, eu-central-1 and ap-southeast-2, and
  published there at `s3://txp-labs-sensitive-data-scanner-<region>/releases/0.5.0/`,
  with a `.sha256` and a `signing.json`. Set `CodeSigningProfileVersionArn`
  to your region's profile (table in `docs/RELEASING.md`) and Lambda refuses
  any code txp-labs did not sign. The Lambda image is in each region's ECR
  repository `sensitive-data-scanner`, by digest.
- **Signed images.** The five container images on GHCR (AWS, Azure, Google
  Cloud, databases, SaaS) are signed with cosign (keyless) and carry an SPDX
  SBOM attestation. `docs/RELEASING.md` › "Verifying a release" has the
  commands.
- **The detection spec on npm, with provenance.**
  `@txp-labs/sensitive-data-spec@0.5.0` is published by this release's
  workflow through npm trusted publishing - no token exists.
- **Every limit documented, each with a switch.** `docs/limitations.md` lists
  what the scanner does not read and why, the setting that turns it on, and
  its default. A store left unread because of a setting says which setting.
  A switch whose feature is not built yet says so when turned on, instead of
  doing nothing.
- **Storage classes, decided from the listing - nothing is read to decide.**
  Each S3 bucket, Azure container and Cloud Storage bucket reports its objects
  and bytes by class, and an **estimated cost to scan** the classes that charge
  for reads, from a dated price table. Archived objects (S3 Glacier Flexible
  Retrieval, Deep Archive, Intelligent-Tiering archive tiers; Azure Archive)
  are reported as **needing a manual restore**, not as unreadable.
- **Settings from Mermera.** A runner connected to Mermera pulls its settings
  with its key (`docs/mermera-config.md`); each run records which value it
  used and where it came from. On AWS the key is kept in a Secrets Manager
  secret of the stack's own, read only by the scanner (about $0.40 a month).

### Changed defaults

- **Parameter Store `SecureString`s are counted, not read** (`SSM_DECRYPT`
  off). They are usually secrets.
- **S3 Glacier Instant Retrieval is not read** unless `S3_READ_GLACIER_IR` is
  on: reading it has a retrieval fee.
- **Azure Cold tier is not read** unless `AZURE_READ_COLD_TIER` is on.
- **Cloud Storage Archive class is not read** unless `GCS_READ_ARCHIVE` is on.
- **Atlassian signs in with an API token** unless `ATLASSIAN_AUTH_MODE=oauth`
  is set: an existing OAuth deployment must set it, or the run stops.
- In "both" mode, Slack DLP events are linked to scanner findings for the same
  item, marked "location only".

All scan costs - reads, requests, compute, exports, retrieval fees - land on
your own cloud bill: the scanner runs in your account. `docs/COST.md` has the
numbers.

### What this release proves, and what it does not

Proven before tagging: the release hosting (buckets, signing profiles, the
release role) was deployed to all seven regions and reviewed; every check in
CI passed. **Proven only by this release's own run:** signing in each region,
the write-once upload rule, the anonymous read-back, cosign signing and npm
provenance - the workflow fails if any of them fails. Not yet proven in a real
account: the storage-class rules and cost estimate, and pulling settings from
Mermera (both are tested against simulated services). Whole-account scans
have run for real in two AWS development accounts and one Microsoft 365
tenant (0.4.0); Azure, Google Cloud and the other SaaS sources remain tested
against simulated services only.
